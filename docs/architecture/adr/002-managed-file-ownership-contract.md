# ADR-002: Managed File Ownership Contract

**Date:** 2026-07-08
**Status:** Accepted
**Deciders:** Lajin M J, AI Scaffold maintainers

## Context

AI Scaffold `v0.8.0` changed the default install surface from a larger scaffold
tree to a core-only install. Older `v0.7.x` installs may still have manifests
that list docs, tasks, and other reference material as managed files, while
newer installs intentionally omit those files unless a future optional pack is
requested.

The update, doctor, repair, and uninstall commands need a clear ownership model
before they can safely change installed projects.

## Decision

AI Scaffold uses four ownership categories:

1. **Scaffold-managed files**
   Files installed or generated by the CLI and safe for future scaffold tooling
   to verify by hash, repair, or update after showing a plan.

2. **Generated project context**
   Files generated from setup inputs, such as `.ai-scaffold.json`,
   `.ai-scaffold/context.md`, `.claude/MEMORY.md`, and
   `.claude/settings-overrides.json`. These are owned by the installed project
   after generation. Future updates must not blindly overwrite them.

3. **Optional pack files**
   Docs, QA, UX, research, CI, templates, and examples that are installed only
   after an explicit request. Pack files must be recorded with the pack name and
   version in the manifest before update/repair/uninstall can manage them.

4. **Protected application files**
   Existing project code, app docs, root package manifests, root README files,
   CI workflows, env files, source directories, and secrets. AI Scaffold must
   not overwrite these by default.

## Manifest Generations

- `v0.7.x` manifests may list larger scaffold docs/tasks/reference files as
  managed.
- `v0.8.x` manifests use the core-only default surface and record only the
  installed core files.

Future update work must treat these as different manifest generations. A
re-baseline step is required before a `v0.7.x` install can be considered fully
updated to the `v0.8.x` ownership contract.

## Consequences

- `ais update` must not mutate versions until file migration and re-baselining
  exist.
- `doctor` may warn about old manifests, but must not assume optional pack files
  are missing in healthy core-only installs.
- `repair` and `uninstall` must start as dry-run plans and rely on operation
  records before making destructive changes.
- Optional packs need explicit manifest records before they can be safely
  updated or removed.
