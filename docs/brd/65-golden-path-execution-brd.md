## 1. Executive Summary

A profile cannot ship when its day-one workflow fails. Today nothing runs that
workflow: `scripts/pre-publish-smoke.sh` greps generated READMEs for command
strings, and item 74's baseline records golden-path success as **null** for
exactly this reason.

Stage 1 generated all five profiles and ran every command their READMEs
document. **The laravel profile's documented path fails on step two** — the
generated project has no `artisan` file — and **node ships four `echo` stubs
that exit `0`**, so an execution gate that treated them as commands would go
green over an unconfigured project.

This item therefore has two halves that must land together: make every
advertised command real, and prove it by execution against a project generated
**from the packed npm artifact**.

## 2. Objectives

| ID | Objective | Measure |
|---|---|---|
| OBJ-01 | A profile's documented day-one commands actually work | Every command a generated README presents as runnable is executed in CI and exits 0 |
| OBJ-02 | The scaffold cannot advertise a capability it does not provide | A placeholder command presented as runnable is a build failure, not a pass |
| OBJ-03 | What is verified is what adopters receive | Execution runs against a project generated from the packed tarball, never from `templates/` or the working tree |
| OBJ-04 | `laravel` means Laravel | The profile contains enough real application for `install`, `migrate`, `test` and a bounded start check to succeed |
| OBJ-05 | Item 74's M-01 gains an honest source | Golden-path success becomes a measured series rather than null-with-a-start-condition |

## 3. Capabilities (ID class `G-xx`)

| ID | Capability | Verifies |
|---|---|---|
| G-01 | Command-contract validation | Every manifest command is either real or `none`; no stub is presented as runnable |
| G-02 | Rendering validation | A non-applicable command renders as prose, never inside a command block |
| G-03 | Golden-path execution | `install` → `migrate` (where declared) → `test` run and pass, per profile |
| G-04 | Bounded health check | A declared `dev`/`serve` command starts, becomes ready, and is terminated — never an unbounded CI invocation |
| G-05 | Packed-artifact provenance | The project under test was generated by the CLI installed from the tarball |

## 5. Functional Requirements

### 5.1 The command contract

| ID | Requirement | Priority |
|---|---|---|
| FR-01 | Every profile SHALL declare each capability (`install`, `dev`, `migration`, `test`, `lint`, `typecheck`, `build`) as either a **real command that performs meaningful work** or the literal `none` | Must |
| FR-02 | A command that exists only to occupy a manifest field — an `echo`, a `true`, a no-op — SHALL be a validation **failure**, not a skip and not a pass | Must |
| FR-03 | Capabilities that genuinely do not apply to a profile SHALL be `none`. Artificial build or typecheck steps SHALL NOT be introduced merely to fill every field | Must |
| FR-04 | A capability declared `none` SHALL render in generated documentation as prose (for example "This profile does not define a build step") and SHALL NOT appear inside a fenced command block | Must |
| FR-05 | The node profile SHALL replace its four `echo` stubs: real commands where the capability is supported, `none` where it is not | Must |

### 5.2 The laravel skeleton (Q-01 = A)

| ID | Requirement | Priority |
|---|---|---|
| FR-10 | The `laravel` profile SHALL generate a runnable Laravel application: an `artisan` entry point, the bootstrap and configuration structure the framework requires, and PSR-4 autoload roots whose directories **exist** | Must |
| FR-11 | The default migration path SHALL be **SQLite**, requiring no database service and no external infrastructure for smoke execution | Must |
| FR-12 | The profile SHALL ship at least one **meaningful** PHPUnit test — one that exercises the application, not `assertTrue(true)` | Must |
| FR-13 | The documented path SHALL be `install` → `migrate` → `test` → a **bounded** start/health verification, and each step SHALL succeed on a freshly generated project | Must |
| FR-14 | If the skeleton proves too expensive to maintain, the correct remedy SHALL be a **separately approved rename to `php`** — never retaining Laravel branding over a non-Laravel project | Must |

### 5.3 Execution

| ID | Requirement | Priority |
|---|---|---|
| FR-20 | Golden-path execution SHALL generate the project using the CLI **installed from the packed tarball**, not from `templates/` and not from the source working tree | Must |
| FR-21 | For each profile, every capability declared real SHALL be executed and SHALL exit 0 | Must |
| FR-22 | A `dev`/`serve` command SHALL be verified as **start → readiness check → terminate**, with an explicit timeout, and SHALL NOT be invoked unbounded | Must |
| FR-23 | A profile with no runnable commands (`generic`) SHALL be recorded as **having no golden path**, explicitly, and SHALL NOT be reported as passing an execution it never performed | Must |
| FR-24 | Failure output SHALL identify the profile, the capability, the exact command, and its exit status and tail output | Should |

### 5.4 Where it runs (Q-03)

| ID | Requirement | Priority |
|---|---|---|
| FR-30 | Golden-path execution SHALL run in the scaffold's normal CI when profile or package inputs change (`templates/**`, `src/cli/**`, `package.json`) | Must |
| FR-31 | Golden-path execution SHALL run in the pre-publish packed-artifact gate, which is the **authoritative release check** | Must |
| FR-32 | CI SHALL provision only the toolchains the executed profiles require, and a toolchain failure SHALL be distinguishable from a golden-path failure | Should |

### 5.5 Both validation layers (Q-04)

| ID | Requirement | Priority |
|---|---|---|
| FR-40 | Static/presence validation SHALL be **retained**, not replaced: it catches a missing or wrongly rendered command, which execution alone does not | Must |
| FR-41 | Execution validation SHALL prove the generated project works. The two layers SHALL be reported separately so a failure names which contract broke | Must |

## 6. Business Rules

| ID | Rule |
|---|---|
| BR-01 | A documented command is a promise. Advertising a capability the profile does not provide is the defect; removing the advertisement is a valid fix, faking the command is not |
| BR-02 | Exit 0 is not evidence. A command that echoes and exits 0 has proven nothing, and the gate must say so |
| BR-03 | Verify the artifact, not the repository. A source tree that works while the tarball does not is a shipped defect (item 26's closure found exactly this class) |
| BR-04 | Nothing long-running goes unbounded in CI. Start, check readiness, terminate |
| BR-05 | "No golden path" is a legitimate, recordable state — and is never rendered as a pass |

---

## 7. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-01 | Golden-path execution SHALL have a per-profile wall-clock bound, and exceeding it SHALL fail loudly rather than hang the pipeline |
| NFR-02 | The gate SHALL be reproducible: a clean run on an unchanged tarball produces the same verdict |
| NFR-03 | No new runtime dependency in the published package. CI-only tooling is acceptable |
| NFR-04 | Toolchain provisioning SHALL pin versions, so a golden-path failure is attributable to the scaffold rather than to a drifting runner image |

## 8. Acceptance Criteria

| ID | Criterion |
|---|---|
| AC-01 | Given the laravel profile generated from the packed tarball, when `composer install`, the documented migrate step and `composer test` run, then all three exit 0 with no database service present |
| AC-02 | Given the laravel profile, when the documented start/health command runs, then it becomes ready within the timeout and is terminated by the harness |
| AC-03 | Given a profile whose manifest declares a command that is an `echo`/no-op, when validation runs, then the build **fails** and names the profile and capability |
| AC-04 | Given a capability declared `none`, when the README is generated, then the phrase appears as prose and no fenced command block contains it (`N/A` never appears as a command) |
| AC-05 | Given the node profile, when validation runs, then every declared capability is real or `none`, and `npm test` executes a real test run |
| AC-06 | Given the generic profile, when the gate runs, then it reports "no golden path" explicitly and does not report a passing execution |
| AC-07 | Given the packed tarball, when the gate runs, then the project under test was generated by the CLI installed from that tarball, provable from the log |
| AC-08 | Given a deliberately broken profile command, when CI runs, then the build fails and the output names the profile, capability, command, exit status and tail |
| AC-09 | Given the change, when the existing static gates run, then they still pass — both layers coexist (FR-40) |
| AC-10 | Given the laravel skeleton, when `php artisan migrate` runs on a fresh generated project, then it succeeds against SQLite — the exact command that fails today |

## 9. Open Questions

**All four resolved by the maintainer, 2026-09-01.**

| ID | Question | Resolution |
|---|---|---|
| Q-01 | What is laravel's correct golden path? | **A — remains Laravel and must become runnable.** Smallest honest Laravel application; reclassifying to generic PHP would preserve the implementation by weakening the product promise. A rename to `php` is the only alternative, and requires separate approval |
| Q-02 | Does a placeholder count as documented? | **No — fail them.** A stub exiting 0 is not a successful golden path. Do not silently skip: implement the capability or stop advertising it |
| Q-03 | Where does it run? | Normal CI when profile/package inputs change, **and** the pre-publish packed-artifact gate, which is authoritative |
| Q-04 | Replace or keep the greps? | **Keep both layers**, reported separately |

## 11. Risks

| ID | Risk | P | I | Mitigation |
|---|---|---|---|---|
| R-01 | **The laravel skeleton cannot be validated in this authoring environment.** The cloud container has PHP 8.4 and composer but its egress blocks Packagist (403); the device VM has neither PHP nor network reach. | **H** | **H** | The skeleton must be proven by CI, which has both. Treat the first CI run as the acceptance evidence for FR-10…FR-13, and do not claim the skeleton works before that run is green |
| R-02 | Laravel's framework download (~100 MB) makes CI slow and Packagist an availability dependency | M | M | Cache composer; scope laravel execution to the packed-artifact gate if per-PR cost proves unacceptable (FR-30 permits input-scoped triggering) |
| R-03 | "Meaningful work" (FR-02) is not self-defining; a naive detector could reject a legitimately trivial command | M | M | The detector's contract is an architecture decision (ADR). Anchor it on the declared-vs-`none` distinction rather than on guessing a command's semantics |
| R-04 | A minimal Laravel skeleton drifts as the framework majors | M | M | Pin the framework major; FR-14's rename is the recorded exit if maintenance cost exceeds value |
| R-05 | Four toolchains on every PR raises CI minutes materially | M | L | FR-30 scopes the trigger to profile/package inputs |
| R-06 | Node's honest answer may be that `lint`/`typecheck`/`build`/`dev` are all `none`, which `doctor`'s verification check could read as an unconfigured project | L | M | `test` remains real, so `checkVerificationConfigured` does not flag it. Confirm during execution |

## 12. Glossary

| Term | Meaning |
|---|---|
| **Golden path** | The commands a generated project's README documents for day one: install, migrate where applicable, test, and start |
| **Placeholder / stub** | A command that occupies a manifest field without performing the work it names |
| **Packed artifact** | The tarball `npm pack` produces — what an adopter installs |
| **Bounded health check** | Start → readiness assertion → termination, under an explicit timeout |
